# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis_grounded | The plan's stated cause, read against the repro-evidence block (live: the posted repro comment, or the repro evidence the drafts quote) | Pass when the stated cause explains the behavior the repro evidence records, and no control run in that evidence rules the cause out. A control rules a cause out when the symptom disappears while the blamed component is held fixed, when a different component shows the symptom, or when the blamed step's input is already wrong before that step runs. Fail when the stated cause contradicts such a control, or when the plan names a cause the repro evidence does not show. A terse cause that matches the evidence still passes. | required |
| scope_bounded | The plan's in-scope and not-in-scope statements, read against the issue body | Pass when the work the plan commits to do is one change for the reproduced behavior. Naming a sibling site of the same defect in the same function, or explicitly deferring a larger idea (not in scope, follow-up, later), still passes. Fail when the plan commits to extra work the issue did not ask for: a rewrite of a subsystem, a dependency migration, a new user-facing option, a new framework, or a multi-front campaign, even if a correct small fix is included. | required |
| stranger_can_start | The plan's files (or modules) and the concrete edit it describes | Pass when the plan names at least one specific file or module and the concrete edit to make there, so a stranger could open that file and start the change without picking the design. Fail when the plan gives no file, or leaves the design open with wording such as somewhere, not sure, whichever is easier, investigate and then decide, or poke around. | required |
| test_observable | The plan's test plan, read against the repro evidence's steps and artifacts | Pass when the test plan names an observable result of this fix: an exit code, an assertion, a specific message, or a concrete before/after behavior tied to the repro. Fail when success is only a feeling (feel fast, feel broken) or only "run the full test suite" or "suite is green" with no observable for the fix itself. Re-running a repro command with an expected exit code or status passes. | required |
| follows_thread_and_policy | The plan comment, read against the thread highlights and the repo-facts contribution policy | Pass only if both parts hold. (1) If a thread highlight from an OWNER, MEMBER, COLLABORATOR, or CONTRIBUTOR names a specific file, patch, or approach to use or to test, the plan comment mentions that direction. If no such highlight exists, this part passes. A comment that does the opposite of that direction and never mentions the named file or patch fails. (2) If the repo-facts contribution policy says AI usage must be disclosed in issues or comments (wording such as "must be disclosed" or "disclosing all AI usage"), the plan comment states that AI was used or names the tool. A policy that only requires human-written comments, responsibility for the code, or disclosure on the pull request and not on issue comments does not fail a comment that lacks a disclosure sentence. "No stated AI policy" passes this part. | required |

## Verdict rule

Accept only when every required check passes. There are no preferred checks. A grade of unclear counts as fail: a plan you cannot verify from the package is not ready to build from. One required fail, or one required unclear, means reject.
